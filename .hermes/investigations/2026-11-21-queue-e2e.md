## Prioritized root causes and reproductions

### P0 — Cross-repo coordinator is not a queue entity

Reproduce with `queue-investigation-matrix.test.ts` for each provider/manual and managed mode. Seed a coordinator with linked projects and a terminal. `observeValidatedAgentEvent` returns false; `AgentSessionManager.registerManagedSession` throws `FOREIGN KEY constraint failed`. Independently launch actual current MCP in that coordinator's temporary work directory: `set_status` returns success but workspace queue is empty.

Sources: `src/main/db/schema.ts:191` FK targets `workspaces`; `activity-queue/agent-source.ts:155` rejects absent workspace; `agent-source.ts:337` also skips questions whose sender is not in that map; `workspace-queue.ts:78` only builds workspace/project context; `services/workspace-service.ts:715` persists XRO phase but needs/status text only go to the event file.

Proposed fix: introduce explicit workspace/coordinator entity ownership throughout sessions, durable reports/questions, queue targets and navigation. Include linked-folder/repo context and persisted request/report text. Do not synthesize a workspace or rebind a live terminal to bypass ownership.

### P1 — Known reporter is not the navigation target; duplicate items

Reproduce: same workspace, reporting terminal 2, unrelated sibling terminal 1 selected. Terminal 2 reports done/blocked with validated identity, then Stop. Queue has two items. The workspace report's durable snapshot names terminal 2, but its target is only `{type:'workspace', workspaceId}`. Open retains terminal 1. New navigation regression verifies the actual pane store result.

Sources: `agent-source.ts:308`; `workspace-queue.ts:139` only supplies terminal context for terminal targets; `renderer/lib/activity-queue-navigation.ts:198` activates workspace without selecting a reporter. Terminal-specific items correctly validate provider/conversation and select their exact pane at line 163.

Proposed fix: preserve a validated report's exact terminal/provider/conversation target through projection and navigation; enrich reporter context. Group task report and turn-end only when identity is proven, retaining separate lifecycle meanings. Do not coalesce siblings by workspace.

### P1 — Questions lack conversation ownership; UI action cannot resolve them

Reproduce: create a structured question from a workspace with two chats; submit an ordinary accepted prompt in its reporting chat; the question stays. Close that chat while a sibling shell remains; it still stays and opens only the workspace. Explicit correlated answer tests pass, including rejection of wrong IDs/recipients/projects/times.

Sources: `agent-source.ts:313` correlation SQL; line 341 snapshot stores only message ID; line 352 workspace-only target; `current-items.ts:48` checks reporter only for `agent-workspace`, otherwise accepts any live workspace; `describe-workspace-item.ts:47` tells the user to answer in the workspace.

Proposed fix: record validated sender conversation/terminal on questions, carry question identity into an explicit reply action, and retire current attention when that owner is closed/replaced. Keep durable question history and strict correlation. Until that exists, explain that ordinary chat replies do not submit a correlated MCP answer.

### P1 — Old/missing MCP identity has both stuck and wrong-clear cases

Actual installed MCP and identity-less current MCP create ownerless reports and cannot retire old chat attention with `working`. New MCP with a valid terminal retires the correct chat, even without a prompt hook. Additional regression: an ownerless manual report can be cleared by a **managed sibling's** accepted prompt, despite no evidence that sibling owned it.

Sources: `mcp-standalone/server.mjs:983` new header; `workspace-service.ts:767` reporter validation; `workspace-service.ts:801` falls back to `managed` when report owner is absent. See [mcp-processes.json](queue-e2e-2026-11-21/mcp-processes.json).

Proposed fix: expose identity/protocol capability in diagnostics and missing-owner context. Replace the legacy managed fallback with an explicit verified dispatch/report association. Treat old records conservatively without guessing ownership. Existing running old MCP processes cannot gain new behavior merely because files changed on disk.

### P1 — Useful provider text and unresolved permission context disappear

Actual Claude supplies reply text, but `agent-hooks/bridge.ts:29` forwards identity/lifecycle fields only. `agent-source.ts:184` builds generic labels. `describe-workspace-item.ts:101` correctly refuses to present these labels as substantive evidence, yielding truthful but unhelpful missing-context messages. Actual Codex's denied/unfulfilled MCP operation shows a further semantic loss: PermissionRequest → Stop replaces permission attention with ready, without a success/failure or resolution reason.

Proposed fix: admit bounded, sanitized provider request/reply/error evidence with provenance; preserve permission identity and require explicit resolution evidence before discarding unresolved context. Do not infer task completion from Stop or infer question answers from generic activity. Include project kind/path and orchestrator role where names alone are ambiguous; current context has project/workspace display names and IDs but no folder/repo path or role.

### P2 — Untagged legacy callback replay remains unsafe

Reproduce for both provider shapes: Stop without a turn ID; explicit identified working clears it; re-execute the old hook later without a turn ID. It is accepted and recreates ready attention. An accepted untagged UserPromptSubmit clears session attention but leaves the workspace report.

Sources: `bridge.ts:7` timestamps **bridge execution**, not the original provider event; `agent-event-order.ts:45` has no durable event ID for untagged replay; `agent-session-manager.ts:263` requires turn ID to continue the workspace.

Proposed fix: define missing-identity capability/ordering semantics, retain stable provider event/turn identity where available, and distinguish replay uncertainty from fresh completion. Current real CLI probes supplied turn IDs; this is a legacy/missing-hook compatibility gap, not a claim that current normal callbacks lack them.

### Separate constraint — Installed/development shared DB collision

`main/index.ts:173` selects daemon by app directory; `db/index.ts:15` selects shared Electron userData; session persistence prunes records against renderer snapshots. Read-time queue filtering then cannot prove the ownership of live orphan PTYs. Snapshot counts are above. Leave the guard intact. Any future isolation/coordination proposal is separate work; the user explicitly required this policy to remain unchanged here.
